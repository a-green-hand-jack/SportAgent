# 重置具体实现，并以现有开源运动产品作为 SportAgent 底座

## Context

SportAgent 已经形成了可接受的北极星：让普通训练者获得安全、可执行、会随真实反馈持续调整的个性化运动指导。但旧 Fitness Agent 原型过早固定了 CLI、多 Agent、训练/营养并行等具体形态，也让项目继续承担用户系统、记录、计划、数据展示和运行时等通用基础设施。

当前真正需要回答的是“SportAgent 应依托什么成熟产品、在哪个边界增加 AI 能力”，而不是继续维护既有实现。仓库同时存在多个历史 feature/memory 分支，也增加了方向尚未收敛时的认知负担。

## Decision

1. 北极星方向保持不变；具体产品形态、首期运动类型和交互方式继续讨论。
2. `main` 与 `dev` 采用同一个无具体产品实现基线；旧 Fitness Agent 源码、数据、测试、依赖与本地环境从活动代码中移除，历史仍可从 Git commit 找回。
3. 长期分支只保留 `main` 与 `dev`：`main` 保存稳定方向和已接受决策，`dev` 用于后续 spike 与集成。
4. 新产品优先依托一个仍在维护的传统运动记录/训练规划开源项目。优先复用其用户、数据模型、记录、计划、历史、可视化、导入导出、交互与部署能力。
5. SportAgent 自有范围聚焦 AI 约束推理、反馈驱动的计划修订、确定性安全边界和领域评测；通用基础设施只保留薄适配层。
6. 在完成候选全景比较、Top 3 架构拆解、Top 2 spike 设计并由 human 接受底座决策之前，不开始新的产品实现或新增产品依赖。

## Consequences

- 好处：项目不再被旧原型架构绑住；讨论可以从用户工作流和开源底座能力出发；减少重复建设基础设施的风险。
- 代价：短期内仓库没有可运行产品；此前的 471 项测试与 uv 环境只属于历史原型，不再是当前基线。
- 历史：模板采用报告和 Git 历史继续证明旧代码曾被完整保留和验证，但它们不是现行产品入口。
- 后续：底座选择必须核对许可证、维护活跃度、扩展边界、数据模型、自托管、隐私和上游同步成本；推荐不等于接受，最终选择由 human 裁决。
- 分支：历史远端分支删除后，未合并内容仍可通过 GitHub/Git 对象审计，但不再作为活动开发线维护。

## Status

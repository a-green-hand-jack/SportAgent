02 维度一：Agent 设计改进
⚙️
Agent Architecture & Logic
编排规则、验证逻辑、输出格式、系统架构
设计 扩展验证维度 P1
当前验证只检查训练量（周组数）。建议扩展以下验证维度：

训练时长验证 — 根据每天的动作数 × 组数 × (次数时间 + 休息时间) + 热身 + 拉伸，估算总时长。如果超过用户设定的 session_duration_minutes: 60 过多（如 >75分钟），应触发调整。Day 2 有 6 个动作共 20 组，加上热身拉伸，实际时长可能接近 80 分钟。

饮食热量验证 — 把推荐的每餐食物的热量加起来，验证总量是否在目标 ±10% 范围内（2247-2747 kcal）。

伤病动作再验证 — 确保多轮修正中新增的动作没有引入对伤病部位有压力的动作。
设计 输出结构化 JSON P1
当前输出是格式化文本。为了支持前端渲染（每日训练卡）、数据持久化和 V2 的计划追踪，agent 应该同时输出一份结构化 JSON。每个训练日为一个独立对象，包含 warmup、exercises[]（每个含 name、weight、sets、reps、rest、cues[]）、cooldown、pre_workout_meal 和 post_workout_meal。这也方便未来做跨周的计划对比和渐进追踪。
设计 起始重量范围约束规则 P2
在 agent 的验证规则中增加：起始重量的范围上下限差距不应超过 30%。如 "10-15kg"（50% 差距）应被要求缩窄为 "12-15kg"。或者更好的方案是给出单一起始值 + 调整指令（如 "12kg 起步，如果第一组轻松完成 12 次则加到 15kg"）。
设计 生成四周具体参数（而非文字描述） P2
当前四周规划仍是文字描述。agent 应该生成四周的具体参数变化，如："第1周 杠铃深蹲 20kg 3×10 → 第2周 20kg 3×12 → 第3周 25kg 3×10 → 第4周 20kg 3×8"。这需要在 agent 逻辑中加入渐进模型的参数化规则，不需要额外知识。
设计 Token 消耗优化 P3
三轮循环共消耗约 71,497 tokens（18832 + 23843 + 28822），这在成本上不可忽视。优化思路：第一轮可以只让 LLM 输出结构化的训练动作列表（不含饮食、教练建议等文本），只有在训练量验证通过后再生成完整的带文本描述的计划。这样前几轮的 token 消耗可以大幅降低。
03 维度二：知识库内容改进
📚
Knowledge Base Content
动作要点、伤病映射、营养数据、热身模板、渐进知识
知识 动作库补充执行要点 (cues) P1
这是当前最大的知识缺口。计划中所有动作只有名称，没有执行提示。每个动作需要 2-3 条核心 cues，存入动作库的 cues[] 字段。示例：

Barbell Squat → ["脚与肩同宽脚尖略外八", "下蹲时膝盖与脚尖同向", "保持挺胸收腹核心收紧"]
Romanian Deadlift → ["背部全程保持平直", "臀部向后推感受腘绳肌拉伸", "杠铃紧贴身体下放"]

工作量估算：80-120 个动作 × 每个 2-3 条 ≈ 240-360 条 cues。这是一次性的工作，建议由有经验的教练审核。
知识 伤病-动作映射矩阵 P1
当前的伤病处理是粗粒度的（"手腕伤 → 避免某些动作"）。需要扩展为一个结构化的矩阵：

伤病状态分级：急性（完全避免负重）/ 恢复中（轻负荷 + 限制角度）/ 陈旧伤（正常训练 + 注意事项）
动作修改建议：对于"可以做但需注意"的动作，给出具体修改方案。如手腕陈旧伤 + 哑铃卧推 → "使用对握哑铃减少手腕桡偏，或佩戴护腕"
替代动作推荐：对于"应该避免"的动作，推荐等效替代。如手腕急性伤 + 杠铃弯举 → 改为绳索弯举（手腕压力更小）

需要覆盖的常见伤病：手腕、肩袖、腰椎、膝关节、脚踝（约 5-8 个部位 × 3 个状态 × 相关动作映射）。
知识 食物热量数据库（用于饮食验证） P2
为了支持 agent 设计中提到的"饮食热量验证"，知识库需要有一个结构化的食物热量数据库。不需要很大——覆盖计划中常用的 100-200 种食物即可。每种食物需要：每 100g 的热量、蛋白质、碳水、脂肪。数据源可以用 USDA FoodData Central 或中国食物成分表。
知识 标准化热身/拉伸模板库 P2
将热身和拉伸方案从"LLM 自由生成"改为"从模板库中匹配"。按训练日类型分类：

下肢主导训练日热身 → [高抬腿、臀桥激活、徒手深蹲、动态弓步走、踝关节绕环]
上肢推训练日热身 → [手臂绕环、肩胛骨活动、俯卧撑(轻)、弹力带肩外旋]

拉伸同理，按当天主要训练的肌群匹配对应的静态拉伸组合。约 8-10 个模板即可覆盖常见的训练日类型。
知识 渐进超负荷的细化知识 P3
当前的渐进规则较为通用。更精细的知识应包括：不同动作类型的最佳渐进方式（复合动作以加重量为主，孤立动作以加次数或组数为主）、渐进停滞时的策略库（暂停组、递减组、1.5 次技术、改变节奏等）、以及基于训练年限的渐进速度参考（初学者每周可加重、中级者每 2-3 周、高级者每月或更慢）。

结论

V1 的核心任务——"根据用户信息生成可执行的个性化健身计划"——在这一版已经基本达成。多轮验证循环的实现是一个关键的架构里程碑，它让系统具备了自我纠错的能力。

接下来的改进分为两条并行的路径：Agent 设计路径侧重于扩展验证维度、优化输出格式、为 V2 做准备；知识库路径侧重于补充动作执行要点和伤病映射，这是提升用户体验的"最后一公里"。

两条路径中优先级最高的分别是：Agent 侧的"扩展验证维度 + 结构化输出"，和知识库侧的"动作 cues + 伤病映射矩阵"。完成这四项之后，V1 就可以认为是一个成熟的版本，可以开始考虑 V2（动态更新与主动交互）的设计了。

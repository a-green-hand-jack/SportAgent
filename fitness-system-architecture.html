AI 健身系统 · 宏观架构

一个基于 LLM/VLM 的个性化健身管理系统

01 三层架构概览
🧠
智能层 — AI Agents
CORE
两个核心 Agent：规划 Agent（LLM 驱动，负责长周期计划生成与动态调整）和视觉 Agent（VLM 驱动，负责实时动作分析与饮食识别）。它们共享同一个用户状态，协同工作。
💾
状态层 — 用户数据与知识
STATE
持久化的用户画像（身体数据、目标、偏好、历史记录）、动态更新的计划状态、以及不断增长的健身知识库（动作库、食谱库、运动科学知识）。这是整个系统的"记忆"。
📱
交互层 — 用户界面
UI
用户与系统的所有触点：文本对话、语音交互、图片/视频上传、计划日历视图、提醒与通知推送。核心原则：最小化用户的主动操作负担。
02 两个核心 Agent
🏗️ 规划 Agent
LLM-Powered · 解决"长周期规划"问题
用户建模模块
收集并持续更新用户的身体数据（体重、体脂、伤病史）、生活数据（作息、工作强度）、目标与偏好
计划生成模块
基于用户模型 + 运动科学知识，生成多粒度计划：年度目标 → 月度阶段 → 周计划 → 每日训练/饮食方案
动态调整模块
根据执行反馈（完成度、体重变化、疲劳度）和突发变化（加班、伤病、旅行），自动调整和重新规划
督促与提醒模块
主动监督执行情况，在合适的时机发送提醒，提供正向激励，必要时调整计划以适应现实
👁️ 视觉 Agent
VLM-Powered · 解决"实时反馈"问题
动作识别模块
从视频中识别用户正在执行的动作类型（深蹲、硬拉、卧推等），匹配到标准动作库
动作评估模块
将用户动作与"金标准"对比，识别关键偏差点（膝盖内扣、腰部代偿、握距不对等），生成具体改进建议
饮食识别模块
通过食物照片识别食材、估算分量和热量，与当日营养目标对比，给出饮食建议
体态评估模块
通过定期拍照追踪体态变化（体型、姿势问题），为规划 Agent 提供视觉维度的输入

04 版本演进路径
V1 · 静态规划 基础规划系统
用户通过问答方式输入个人信息（身高体重、目标、可用时间、器材等），LLM 生成个性化的训练计划和营养方案。这是一个"一次性生成"的系统，验证核心价值：AI 能否生成足够专业且个性化的健身方案。
文本问答 计划生成 营养方案 知识库查询
V2 · 动态更新 持续追踪与自更新
Agent 开始具备"主动性"。它会定期提醒用户更新体重等数据，根据执行情况自动调整计划，从互联网抓取新的食谱和训练方法来丰富知识库。系统从"工具"进化为"助手"。
主动提醒 数据追踪 计划自调整 知识库自更新 日程感知
V3 · 视觉反馈 动作分析与饮食识别
引入视觉 Agent。用户可以上传训练视频获得动作纠正反馈，拍摄食物照片自动记录饮食。系统获得了"眼睛"，能够理解用户的真实执行质量，而不仅仅依赖用户的文本汇报。
动作识别 动作纠正 食物识别 热量估算 体态追踪
V4 · 全闭环 完全自主的健身管家
两个 Agent 深度协同。视觉 Agent 的发现自动反馈给规划 Agent（比如发现膝盖内扣 → 调整训练计划加入髋关节稳定性训练）。系统达到"人只负责执行"的理想状态，所有规划、追踪、调整都是自动的。
双Agent协同 全自动化调整 个性化进化 长期健康追踪 伤病预防
05 关键设计问题
系统的边界在哪里？
系统不替代医生。它处理的是"健康人的健身优化"，而非"伤病的治疗"。遇到超出能力范围的问题（疑似伤病、异常指标），系统应该明确建议用户就医，而不是试图处理。
Agent 的主动性边界？
Agent 需要在"太烦人"和"不够主动"之间找到平衡。关键原则：高价值低频打扰。比如"你今天的训练计划已就绪"比"你该去锻炼了"更好。系统应该像一个得体的管家，而不是唠叨的教练。
知识的可信度如何保证？
LLM 的健身知识并不总是正确的。系统需要一个经过审核的"核心知识库"作为 ground truth，LLM 的推理要基于这个知识库而不是自由发挥。互联网抓取的新知识需要经过验证才能纳入。
用户的参与成本如何控制？
"用户只负责执行"是理想目标，但现实中用户需要上传数据。设计原则：每次交互不超过 30 秒。食物拍照、体重记录都要做到一步完成。训练视频可以自动录制（如果有支架）。

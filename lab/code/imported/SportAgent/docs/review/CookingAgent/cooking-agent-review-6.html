02 问题分析
🔴周二热量不达标：计算 2378 kcal (-11.0%)P0
唯一未达标天。根因是"金枪鱼红薯"的热量被系统性高估：标注 499 kcal，计算 421 kcal（+18.4% 偏差）。问题出在红薯——250g 红薯实际只有 ~215 kcal，但 LLM 可能高估了烹饪后的热量。同样的菜在周四出现时也有 +18.3% 偏差。

修复建议：这道菜是训练后加餐的主力菜品（出现 2 次），需要校正其热量估算。可以增加红薯用量（250g→300g）或加一个水煮蛋来补足缺口的 ~80 kcal。更根本的解法是接入食物数据库做确定性计算。
🟠标注系统性偏高 3-9%P1
v6 的标注值系统性高于计算值（所有 7 天标注都 ≥ 计算值），平均偏高约 4.6%。v5 也有类似现象（偏高 3-5%）。这意味着 LLM 的修正循环在"达标"时，实际热量可能略低于它认为的水平。

对于周二：LLM 认为 2549 kcal（-4.6%），觉得差不多够了。但实际只有 2378 kcal（-11.0%）。如果修正循环能基于确定性数据库而非 LLM 估算，这个差距就能被消除。
🟡"年糕香蕉蜂蜜片" — 实为饭团+香蕉，不是年糕P2
菜名叫"年糕"，配方是"大米 140g 捏成紧实饭团"。这不是年糕（年糕是糯米制品，热量约 200 kcal/100g），而是普通米饭捏成饭团。菜名和配方不一致会让用户困惑。建议改名为"饭团香蕉蜂蜜片"或直接叫"香蕉饭团"。
🟡高蛋白松饼需要 7 个蛋的蛋白（220g）P2
和 v5 同一问题。分离 7 个蛋的蛋白操作复杂且浪费蛋黄。建议用大豆分离蛋白粉替代——PlanAgent 已经在补剂列表中推荐了"无乳糖蛋白粉"。1.5 勺蛋白粉 ≈ 220g 蛋白的蛋白质含量，且操作简单。
🟡post_workout 热量偏高（600-810 kcal）P2
系统自检正确检测到 4 个 post_workout 超过 600 kcal 建议上限。这些训练后加餐的碳水偏高（如鸡胸饭 320g 米饭）。虽然训练后可以摄入更多碳水，但 800+ kcal 的 post_workout 已经是一顿正餐的量。建议将 post_workout 上限设为 700 kcal，超出部分转移到正餐。
03 系统级成就
🔗端到端数据流首次完整
PlanAgent 的 5 训练日 + 2 休息日 → CookingAgent 正确解析 → 训练日有 pre/post_workout，休息日没有。这个数据流是整个系统的核心，经过 v4→v5→v6 三版终于打通。
🥩post_workout 蛋白质全部 ≥35g
5 个训练日的 post_workout 蛋白质范围 48-69g，远超 35g 阈值。训练后的蛋白质窗口被充分利用——鸡胸饭(69g)、金枪鱼红薯(48-64g)、虾仁汤面(58g)。
⚡pre_workout 碳水为主、低蛋白
训练前加餐全部以碳水为主：年糕香蕉片(5g pro)、花生酱吐司(13g pro)、快手红薯(6g pro)、燕麦能量球(14g pro)。热量 310-423 kcal，集中在训练前 30-60 分钟。这正是训练前加餐的正确策略。
📊蛋白质 7/7 天全部达标
最低 157g（周二），最高 191g（周四），全部远超 140g 目标。六版演进中首次实现蛋白质全周达标 + 训练日结构正确的"双重达标"。
04 下一步改进
1.接入食物营养数据库（确定性计算）P0
v6 暴露了 LLM 估算的最后一个 gap：标注值系统性偏高 3-9%，导致周二实际不达标但 LLM 以为达标了。修正循环的架构已经成熟，只差最后一步——把"LLM 估值"替换为"查表计算值"。这是从"大部分准确"到"全部准确"的关键一步。

具体实现：建一个 200-300 种常用食材的营养数据库（每 100g 的 kcal/protein/carb/fat），在修正循环中用数据库计算替代 LLM 估算。数据源推荐中国食物成分表或 USDA FoodData Central。
2.校正"金枪鱼红薯"等高偏差菜品P1
金枪鱼红薯出现 2 次，两次都有 +18% 偏差。在没有数据库的短期方案中，可以手动调整这道菜的食材用量（红薯 250g→300g），或在修正循环中对已知高偏差菜品增加 buffer。
3.蛋白粉替代纯蛋白P1
连续两版（v5、v6）出现"需要 7 个蛋的蛋白"问题。PlanAgent 已经推荐了"无乳糖蛋白粉"，CookingAgent 应该读取这个补剂信息并在奶昔/松饼类食谱中优先使用蛋白粉。
4.post_workout 热量上限 700 kcalP2
训练后鸡胸饭 810 kcal 和 751 kcal 偏高。建议将 post_workout 硬上限设为 700 kcal，超出部分通过增加正餐热量来补偿。
5.菜名 vs 配方一致性检查P2
"年糕香蕉蜂蜜片"实际是米饭饭团——菜名和配方不一致。建议在生成后加一个简单的一致性检查：菜名中的关键食材（年糕、面条、红薯等）是否在配方食材列表中出现。

A：首个可交付用户的版本

v6 的核心突破是训练日数据流修复。这是 v4 以来的最高优先级 bug，经过三版迭代终于解决。5 个训练日全部正确生成了 pre_workout（碳水为主，310-423 kcal）和 post_workout（高蛋白 48-69g，500-810 kcal），2 个休息日没有训练加餐。PlanAgent → CookingAgent 的端到端数据流首次完整运作。

从 v1(C+) 到 v6(A) 的演进路径总结：基础精度(v1-v2) → 修正循环(v3) → 热量全面达标(v4) → 多样性突破(v5) → 训练日数据流(v6)。每一版都解决了前一版最紧急的问题，agent 的迭代效率很高。

这是第一个可以让用户"不动脑子跟着执行"的版本。用户拿到这份计划后：训练日知道练前吃什么、练后吃什么；休息日三餐 + 加餐安排清晰；每天热量和蛋白质基本达标；26 道菜不重复不无聊；食谱步骤具体可执行。唯一的系统性缺陷是 LLM 标注偏高导致周二实际热量不达标——这个问题的根本解法是接入食物营养数据库，让修正循环基于确定性计算而非 LLM 估算。

📊 热量验算核心发现
好消息：标注精度大幅提升。33 道菜中 28 道标注偏差 ≤15%，多数在 5-7% 范围内，说明 LLM 的热量估算能力比 v1 有明显改善。只有 3 道菜偏差超 15%：彩椒牛肉丝（+22.6%）、金枪鱼红薯（+20.8%）、金枪鱼意面沙拉（+18.3%），且全部是标注偏高——LLM 高估了这几道菜的热量。

坏消息：3 天热量严重不达标，且系统未自动修正。周二实际 2160 kcal（差 512 kcal）、周六实际 2056 kcal（差 341 kcal）、周日实际 1893 kcal（差 504 kcal）。系统自己标注了"4/7 天达标"，说明它知道有问题，但没有触发自动修正循环——这是 v1 review 中指出的同一个问题，尚未解决。

另一个层面：即使标注值接近真实值，周二的标注值 2363 kcal 本身也与目标 2672 kcal 差了 -11.6%，说明 LLM 在编排食谱时就没有凑够目标热量。这是"编排能力"的问题，不只是"计算精度"的问题。

04 具体问题清单
🔴 自动修正循环仍然缺失 P0
系统标注"热量达标 4/7 天"并在底部给出偏差提示，但没有触发自动调整。这是 v1 review 中就指出的核心架构问题。CookingAgent 需要在检测到偏差 >10% 时，自动增加食材分量或补充加餐，而不是把"建议调整"留给用户。这不是 prompt 层面能解决的——需要在 agent 的控制流中加入循环逻辑。
🔴 周二训练后餐蛋白质严重不足 P0
周二 post_workout 是"豆腐莓果奶昔"（~10g 蛋白质），全天蛋白质仅 102g（目标 140g，缺口 27%）。训练后餐是全天蛋白质的关键锚点，需要一条约束规则：post_workout.protein ≥ 35g。这是知识层面的缺失——CookingAgent 不知道训练后蛋白质的重要性。
🟠 休息日热量系统性偏低 P1
周六 2056 kcal（差 341）、周日 1893 kcal（差 504）。两个休息日都只安排了 4 餐且没有 pre/post_workout 加餐，但没有在正餐中补偿缺失的加餐热量。休息日虽然热量目标低于训练日，但也只低了 ~275 kcal，不应该低 400-500 kcal。需要一条规则：休息日要么增加每餐分量，要么增加一份高质量加餐来补偿没有训练加餐的缺口。
🟠 周三没有零食/加餐，只有 4 餐 P1
训练日结构应该是 5 餐（breakfast + pre + post + dinner + snack），但周三只有 4 餐（没有 snack）。虽然热量恰好够了（2797 kcal），但这意味着每餐热量偏高。pre_workout 的"香蕉燕麦能量球"标注 667 kcal，对于训练前加餐来说偏重。更好的做法是降低 pre_workout 热量并补充一份 snack。
🟡 90g 全麦面包 = "约 3 片"还是"两片"？ P2
周一花生酱吐司标注"90g (约3片)"，周五同一道菜标注"90g (两片)"，周六三明治也是"90g (两片)"。90g 全麦面包大约是 2.5 片（每片约 35-40g）。应该统一标注，否则用户会困惑到底用几片。
🟡 鸡蛋个数标注不一致 P2
150g 鸡蛋有时标注"约3个"（周一松饼），有时标注"两个鸡蛋"（周六三明治、周日早餐盘）。150g ÷ 50g/个 = 3 个蛋。"两个鸡蛋"对应的应该是 100g。同一道菜（蔬菜鸡蛋全麦三明治）周三用 200g"约4个"，周六用 150g"两个鸡蛋"——后者标注有误。
05 做得好的地方
✅乳糖限制完全合规
全周零乳制品。豆腐替代奶酪、椰子油替代黄油、豆浆替代牛奶，所有替换都合理。v1 的 cottage cheese 问题已彻底修复。
✅蛋白质来源丰富
覆盖 6 大类：鸡胸肉、牛里脊、猪里脊、鳕鱼、金枪鱼、豆腐/毛豆 + 鸡蛋。比 v1 的"鸡胸肉+蛋白粉"有质的飞跃。
✅菜品多样性达标
所有菜品最多出现 2 次，满足"同一道菜一周 ≤ 2 次"的约束。食谱风格多样：中式炒菜、日式清蒸、西式三明治/沙拉、创意奶昔。
✅食谱可执行性高
每道菜步骤清晰，食材用量精确到克数，准备时间标注实用。大部分菜品简单易做，适合健身人群的日常烹饪能力。"减脂版麻婆豆腐"、"香蕉燕麦能量球"等创意菜品是亮点。
✅热量标注精度大幅提升
85% 的菜品标注偏差 ≤15%（v1 约 60%），多数在 5% 左右。说明 LLM 的估算在"合理范围"内，虽然仍需确定性计算替代，但进步明显。
✅采购清单完整
39 种食材按分类汇总，用量准确。"水 200g"这种条目可以去掉（不需要购买），但整体实用性很好。
06 对 CookingAgent 的改进建议（系统层面）
🔧 必须实现自动修正循环 P0 · 架构
这是连续两个版本的同一个问题。CookingAgent 的控制流应该是：生成 → 验证（热量±10%、蛋白质≥90%目标）→ 不通过则自动调整 → 再验证 → 最多 3 轮。当前只做到了"生成 → 验证 → 输出提示"，缺少中间的自动调整环节。
📏 增加"每餐蛋白质下限"约束规则 P0 · 规则
新增规则：post_workout.protein ≥ 35g，lunch/dinner.protein ≥ 25g。这可以防止周二那种"训练后只给 10g 蛋白质"的极端情况。同时增加每日蛋白质验证维度。
📏 增加"休息日餐食结构"约束规则 P1 · 规则
休息日没有 pre/post_workout 加餐，但热量目标只比训练日低 ~10%。当前的休息日少了一餐但没有补偿，导致热量系统性不足。规则：休息日正餐平均热量应比训练日正餐高 ~15%，或者增加一份 300-400 kcal 的加餐。
📏 统一食材单位标注规范 P2 · 规则
在 system prompt 或规则集中明确：鸡蛋 1 个 = 50g；全麦面包 1 片 = 35g；大米标注一律用"(煮熟)"并注明"(生重约 Xg)"。避免同一食材在不同位置标注不一致。

B从 C+ 进步到 B，但核心架构问题未解决

v2 在表面质量上有明显进步：饮食限制合规了、菜品更多样了、蛋白质来源更丰富了、单菜热量标注更准了。这些是 prompt 层面优化的成果。

但深层架构问题没有解决：自动修正循环仍然缺失，3/7 天热量不达标只给了文字提示而没有自动修正；缺少蛋白质每日验证，导致周二出现 102g 的极端低值；休息日没有补偿"少一餐"的热量缺口。

这些问题不是通过改 prompt 能解决的——它们需要在 CookingAgent 的控制流中增加验证-修正循环，在规则集中增加每餐蛋白质下限和休息日餐食结构约束。这是 v3 需要重点突破的方向。

评分说明：A = 可交付用户，B = 大部分可用但有明显缺陷，C = 基本框架有但问题较多，D = 不可用。v2 从 C+ 升至 B，下一步目标是 B+ → A-。

🎉热量和蛋白质首次全周达标
这是四个版本以来第一次实现 7/7 天热量全部在 ±10% 以内（确定性验算口径）。蛋白质也全部 ≥140g。标注精度进一步提升——34/35 道菜标注偏差 ≤15%，只有金枪鱼红薯（+25.6%）一道超标。

周二、周四、周六、周日的计算值与目标偏差均在 ±2% 以内——接近完美。这说明修正循环 + LLM 的热量估算在"简单食材组合"上已经足够准确。
02 核心问题
🔴全周 7 天都是休息日 — 训练日哪去了？P0
这是最大的问题。用户的训练计划通常有 4-5 个训练日，但 CookingAgent 生成了 7 天休息日的饮食方案。可能原因：CookingAgent 没有正确接收 PlanAgent 的训练日安排，或者接收了但在生成过程中丢失了。

后果很严重：训练日热量目标是 2672 kcal，休息日是 2397 kcal。如果用户在训练日吃休息日的量，每天会少摄入 ~275 kcal，严重影响增肌效果。更关键的是训练日需要 pre_workout 和 post_workout 两个额外加餐，休息日方案完全没有这些。

这是 CookingAgent 与 PlanAgent 之间的数据流问题，不是 CookingAgent 自身的生成质量问题。需要确认训练日信息是否正确传递给了 CookingAgent。
🔴陷入 AB 模板循环 — 5 道菜各出现 3 次P0
这是 v3 没有的问题，v4 反而恶化了。一周形成了两套固定模式：

A 天（周一三五）：红薯鸡蛋早餐盘 → 鸡胸肉西兰花饭 → 各异的晚餐
B 天（周二四六）：奇亚籽隔夜燕麦 → 家常豆腐炒蔬菜 → 三文鱼/照烧三文鱼
盐水毛豆穿插出现 3 次

用户连续一周吃这个方案，会发现自己在重复吃同样的早餐和午餐。这严重违反"用户不动脑子就能执行"的目标——因为用户会主动拒绝再吃第三次鸡胸肉西兰花饭。

根因分析：CookingAgent 为了确保热量达标，倾向于复用已验证过的"安全"食谱组合，因为它知道这些组合的热量是准的。这是精确性和多样性之间的 trade-off——v4 在精确性上取得突破，但代价是多样性崩塌。解法是约束 每道菜一周最多出现 2 次，同时扩充已验证的食谱库。
🟠希腊酸奶 — 乳糖不耐受边界案例P1
周一零食是"希腊酸奶 270g（无乳糖型或乳糖酶处理款）"。虽然标注了无乳糖型，但无乳糖希腊酸奶在中国市场很少见，用户很可能买到普通含乳糖版本。更安全的做法是用豆腐/豆浆基底的替代品。这个问题反映了饮食限制过滤依然是软约束——系统试图通过标注"无乳糖型"来规避限制，而不是从根本上换掉这个食材。
🟡菜名自相矛盾P2
周五有一道菜叫"训练后金枪鱼红薯（休息日适配版）"——名字里带"训练后"但当天是休息日。这说明这道菜是从训练日菜谱复制过来加了个后缀，而不是真正为休息日设计的。系统也检测到了它作为 snack 热量 465 kcal 超标。

04 根因分析：为什么热量达标了但多样性崩了？
🔍精确性 vs 多样性的 trade-off
v4 暴露了一个深层矛盾：当 CookingAgent 被强化要"确保热量达标"时，它倾向于复用已成功验证的食谱组合。因为它知道"红薯鸡蛋早餐盘 ≈ 480 kcal"是靠谱的，所以每隔一天就用一次。这和人类行为很像——你如果要求一个厨师"每道菜热量必须精确"，他也会倾向于重复使用已掌握的菜式。

解法不是简单地加"每道菜最多 2 次"约束（虽然这也要加），而是扩充"已验证食谱库"。目前系统大约只有 15-20 道可靠菜品，需要增加到 40-50 道，让 agent 有更多"安全"选项可以轮换。
05 v5 改进方向
1.修复训练日数据流P0
检查 CookingAgent 的输入：PlanAgent 的训练日安排是否被正确传递？如果传递了，CookingAgent 是否正确解析并区分了训练日/休息日？这是一个 agent 间通信问题，不是生成质量问题。训练日必须有 pre_workout + post_workout 加餐，且热量目标应为 2672 kcal。
2.强制多样性约束 + 扩充食谱库P0
硬约束：任何菜品一周最多出现 2 次（当前 5 道菜各出现 3 次）。同时需要扩充 agent 可用的食谱范围——目标是至少 40 道经过验证的菜品，覆盖不同蛋白质来源 × 不同碳水 × 不同烹饪方式的组合矩阵。没有足够的食谱库，agent 就会在精确性压力下退回到复用模式。
3.饮食限制过滤从软约束升级为硬约束P1
"希腊酸奶（无乳糖型）"说明系统在试图"绕过"限制而非"遵守"限制。乳糖不耐受的禁用清单应该在食材选择前做确定性过滤，禁止任何乳制品出现（包括"无乳糖版"的乳制品，因为用户不一定买得到）。
4.引入食物营养数据库（持续优先）P1
虽然 v4 标注精度已经很高（97% ≤15%），但金枪鱼红薯仍然偏差 25.6%。确定性计算仍然是长期可靠性的保障——尤其当食谱库扩充后，新菜品的热量估算不一定像老菜品那么准。

B+：数值能力达到 A 级，但被多样性和训练日缺失拖回 B+

v4 在数值精确性上取得了决定性突破：热量 7/7 达标、蛋白质 7/7 达标、标注精度 97%。如果只看这些指标，这是一份 A- 水平的计划。修正循环 + LLM 估算的组合在休息日场景下已经足够可靠。

但两个系统性问题把评级拉了回来：全周没有训练日（数据流 bug），以及 5 道菜各出现 3 次（多样性崩塌）。前者是 agent 间通信问题，后者是精确性压力下的策略退化。

从"用户不动脑子执行"的角度：如果用户真的连续吃一周，周三到周五他就会抱怨"又是红薯鸡蛋早餐盘 + 鸡胸肉西兰花饭"。用户不会因为热量精确而忍受无聊——但一定会因为无聊而放弃整个计划。多样性不是锦上添花，是用户留存的底线。

下一步最关键的两件事：① 修复训练日数据流（确保 CookingAgent 能区分训练日/休息日）、② 扩充食谱库 + 强制多样性约束（最多 2 次 + 40 道可验证菜品）。数值能力已经证明了，现在需要让这份计划"好吃且不无聊"。

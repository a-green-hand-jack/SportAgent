CookingAgent · System Review

CookingAgent 系统级改进方案

不是评价某一份具体的饮食计划，而是从 CookingAgent 的架构设计、知识库需求、操作流程和约束规则四个维度分析需要做什么改进，使其能持续稳定地生成"用户不动脑子就能执行"的饮食方案。
01 当前核心问题诊断
🔴 LLM 在"编造"热量数字，而非计算 P0
这是当前最根本的问题。CookingAgent 让 LLM 同时做两件事：生成食谱 + 估算热量。但 LLM 不擅长精确的数值计算，导致标注热量与食材实际热量严重不一致（偏差高达 40%）。热量计算应该从 LLM 的职责中剥离出来，改为确定性计算：LLM 负责选择食材和分量 → 系统查食物营养数据库 → 确定性地算出热量。LLM 永远不应该自己"猜"一个热量数字。
🔴 验证发现问题后没有自动修正 P0
系统已经能检测到热量偏差（如周二 -16.9%、周四 -18.4%），但只是输出一条"建议调整"的提示，没有自动修正。CookingAgent 需要和 PlanAgent 一样实现"生成-验证-修正"的多轮循环。验证不通过的天数应该自动触发重新生成或调整，直到所有天数的热量和蛋白质都达标。
🟠 饮食限制过滤不够严格 P1
用户标注了"乳糖不耐受"，但周六零食出现了 200g 农家奶酪（含乳糖）。这说明 CookingAgent 的饮食限制过滤是软约束（LLM 自由判断）而非硬约束（系统级过滤）。饮食限制应该像伤病-动作映射一样，在食材选择阶段就做确定性的排除，不能依赖 LLM 来"记住"。

💡 核心设计原则：LLM 负责创意，系统负责精确
和 PlanAgent 的"知识库约束 + LLM 推理"模式一致，CookingAgent 也应该明确分工。LLM 负责的是"创造性编排"：选择什么食材搭配、设计什么烹饪方式、安排什么样的餐食结构，让食谱既营养又好吃。系统负责的是"精确计算和硬约束"：热量计算、蛋白质汇总、饮食限制过滤、多样性检查。两者不能混为一谈——让 LLM 去算热量就像让厨师去做会计的工作，不是他的强项。
03 知识库需要补充的内容
📊 食物营养数据库 知识库 P0
这是 CookingAgent 最急需的知识库补充。每种食物需要结构化的营养数据：每 100g 的热量、蛋白质、碳水化合物、脂肪、膳食纤维。V1 阶段不需要覆盖所有食物，覆盖 CookingAgent 常用的 200-300 种即可（肉类、鱼类、蛋奶、谷物、蔬菜、水果、油脂、调料、坚果）。数据源建议使用中国食物成分表或 USDA FoodData Central。关键是要有足够的中国常见食材覆盖。
当前状态：不存在，LLM 自行估算热量
目标状态：结构化数据库，支持按食材名查询营养成分，计算过程完全确定性
🚫 饮食限制-食材映射表 知识库 P0
类似于 GYMAgent 的"伤病-动作映射矩阵"，CookingAgent 需要一个"饮食限制-食材映射表"。这是一个确定性的排除清单，不应该让 LLM 自己判断哪些食材该排除。
乳糖不耐受 → 排除：牛奶、奶酪、酸奶、黄油、奶油、冰淇淋… 允许：无乳糖牛奶、豆浆、椰奶、硬质奶酪（含乳糖极少）…
不吃油腻 → 排除烹饪方式：油炸、红烧（大量油）、干煸… 限制用油量：每道菜用油 ≤ 10g
素食 → 排除所有动物肉类，保留或排除蛋奶（取决于素食类型）
过敏（坚果/海鲜/麸质等）→ 排除对应食材及其衍生物
🔄 等营养素替换矩阵 知识库 P1
当系统需要替换某种食材（因为限制、偏好或多样性要求），它需要知道"用什么替换等效"。这不是 LLM 随便选一个替代品，而是有数据支撑的等营养素替换。比如 150g 鸡胸肉（约 250kcal、46g 蛋白质）可以替换为：180g 鳕鱼（约 250kcal、42g 蛋白质）或 200g 虾仁（约 240kcal、48g 蛋白质）或 250g 老豆腐（约 260kcal、25g 蛋白质，蛋白质偏低需补偿）。这个矩阵可以从食物营养数据库中自动生成，按蛋白质来源分组。
📏 食材重量标准化知识 知识库 P1
解决"300g 大米是生还是熟"这类歧义问题。知识库中需要维护常见食材的"生熟换算比"和"常见单位换算"。比如：大米生熟比约 1:2.3（100g 生米 ≈ 230g 熟米）；全麦面包 1 片 ≈ 35-40g；鸡蛋 1 个（中等）≈ 50g（去壳）；香蕉 1 根（中等）≈ 120g（去皮）。CookingAgent 在输出时应该统一使用生重（因为用户购买和称量的是生食材），并在需要时标注熟重参考。
🍽️ 菜谱模板库（可选，V1.5+） 知识库 P2
当前的食谱完全由 LLM 生成，质量依赖于 LLM 的烹饪知识。更稳定的方案是建立一个经过验证的"菜谱模板库"，每个模板包含：菜名、食材列表（含营养数据链接）、烹饪步骤、可替换的食材选项、标签（高蛋白/低碳/快手/素食等）。LLM 的角色从"创作食谱"变为"从模板库中选择和搭配"——这大幅提高了可靠性。V1 阶段可以先让 LLM 自由生成，但长期来看模板库是更可靠的方案。初始可以收集 50-100 个经过验证的健身餐食谱。
04 操作流程需要增加的环节
🔢 确定性热量计算环节 流程 P0
在 LLM 生成食谱之后、输出给用户之前，系统必须插入一个确定性计算环节。对于每道菜的每种食材，查询营养数据库获取每 100g 的营养数据，乘以实际用量，得到该食材的热量和营养素贡献，然后逐菜汇总、逐餐汇总、逐日汇总。LLM 输出的热量标注应该被系统计算的结果覆盖，而不是直接使用。这个环节需要 LLM 输出的食材名称能准确匹配到营养数据库中的条目——这可能需要一个"食材名称标准化"的步骤（比如 LLM 写"鸡胸肉"，系统匹配到数据库中的"鸡胸肉,去皮,生"）。
🔄 生成-验证-修正循环 流程 P0
与 PlanAgent 的多轮循环一致。验证维度包括：

每日热量达标 — 每天的实际热量与目标偏差 ≤ ±10%。训练日和休息日使用不同的热量目标。
每日蛋白质达标 — 每天的蛋白质总量 ≥ 目标值的 90%。
饮食限制合规 — 所有食材均不在禁用清单中。
菜品多样性 — 同一道菜一周内最多出现 2 次。

不通过时，反馈给 LLM 的修正指令应该是具体的（如"周二总热量差 452kcal，请增加 post_workout 的米饭分量从 250g 到 350g，并增加一份 200kcal 的加餐"），而不是模糊的"请调整"。
🚫 食材预过滤环节 流程 P0
在 LLM 生成食谱之前，系统先根据用户的饮食限制生成一份"禁用食材清单"和"限制烹饪方式清单"，作为硬约束注入 LLM 的 prompt。同时在 LLM 输出之后，再做一次确定性检查——扫描所有食材名称，检查是否有任何食材命中禁用清单。这是双重保障：prompt 级别的软约束 + 输出级别的硬验证。
📦 结构化输出格式 流程 P1
CookingAgent 的 LLM 应该输出结构化的 JSON（食材名称、克数、烹饪步骤），而不是直接输出给用户看的 Markdown。原因有三：（1）结构化数据方便系统做热量计算（查营养数据库需要标准化的食材名和精确的克数）；（2）方便做食材汇总生成采购清单；（3）方便前端渲染成不同的展示格式。最终面向用户的 Markdown/HTML 格式应该由一个独立的"渲染"步骤从 JSON 生成，而不是让 LLM 直接写最终格式。
05 需要增加的约束规则
🎯 热量分配规则 规则
训练日热量 = TDEE × 活动系数 + 盈余，休息日热量 = TDEE + 较小盈余。每餐的热量占比应有推荐范围，而非随机分配。比如：早餐 20-25%、午餐/训练后餐 30-35%、晚餐 25-30%、加餐 10-15%。训练前加餐以碳水为主（碳水:蛋白质 ≈ 3:1），训练后餐以蛋白质+碳水为主（蛋白质:碳水 ≈ 1:2）。
🔁 多样性约束规则 规则
同一道完整菜品一周最多出现 2 次。同一种蛋白质来源（如鸡胸肉）作为主菜一周最多 3 次。一周内应覆盖至少 3 种蛋白质来源（禽肉、鱼虾、红肉、豆制品、蛋类中至少 3 类）。碳水来源也应多样化（米饭、面条、红薯、土豆、藜麦等轮换）。
⏱️ 烹饪复杂度约束 规则
每天的总烹饪时间不应超过用户设定的阈值（默认 60 分钟/天，可配置）。至少有 1-2 天是"快手日"（每餐准备+烹饪 ≤ 15 分钟）。早餐和零食的准备时间应 ≤ 10 分钟。如果用户标记了"不擅长烹饪"，所有菜品限制在 5 步以内。
📏 分量标注规范 规则
所有谷物/面条/薯类标注生重，并注明"(生重)"。调料不使用"少许/适量"，统一用克数+日常参照（如"盐 3g，约半茶匙"）。食材用量精确到 5g 或 10g 整数（用户不会称出 43g 的橄榄油）。鸡蛋统一标注"X 个（约 Yg）"。
06 用户体验层面的增强
🔀 备餐建议（Meal Prep） 体验 P2
很多健身用户会在周末一次性准备多天的食物。CookingAgent 应该能识别一周内重复出现的食材和菜品，输出一份"备餐建议"——比如"鸡胸肉本周共需 740g，建议周日一次煎好切片冷藏，每次使用前微波加热即可"。这大幅降低了用户每天的烹饪负担。
🏪 采购清单优化 体验 P2
当前的采购清单已经是一个很好的功能，但可以进一步优化。按购物动线分组（蔬菜区 → 肉类区 → 调料区 → 冷藏区），而非按字母排序。标注保鲜建议（"鸡胸肉 740g — 分 3 份冷冻，每次取 1 份解冻"）。区分"常备调料"（家里可能已有，如盐、酱油）和"本周需购"（本周特别需要的食材）。
📊 每日 / 每周营养概览 体验 P2
在饮食计划的开头或结尾，提供一个一周的营养概览表：每天的实际热量 vs 目标、蛋白质 vs 目标、碳水和脂肪的比例。以及一周平均值。这让用户对自己的饮食有一个全局视角，也方便 MonitorAgent 做后续的追踪对比。

总结

CookingAgent 的当前输出在"形式"上已经接近可交付——有完整食谱、有采购清单、有烹饪步骤。但在"数值精确性"上存在根本性缺陷：LLM 在编造热量数字，导致标注热量与实际热量严重不一致，进而导致接近一半的天数热量不达标。

解决这个问题的核心不是调整 prompt，而是在架构层面把"计算"和"创意"分离。引入食物营养数据库 + 确定性热量计算环节 + 多轮验证修正循环，让 LLM 只负责它擅长的事情（选食材、写步骤、搭配餐食），把它不擅长的事情（精确计算、硬约束过滤）交给确定性系统。

这个改进思路和 PlanAgent 的演进路径完全一致——PlanAgent 也是经历了"训练量验证 bug → 引入确定性验证 → 多轮循环自动修正"的过程。CookingAgent 需要走同样的路。

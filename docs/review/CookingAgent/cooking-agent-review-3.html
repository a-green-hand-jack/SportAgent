📊核心发现：系统认为 7/7 达标，实际只有 4/7
系统标注"热量达标 7/7 天"，这说明自动修正循环确实在工作——v2 时系统自己承认只有 4/7 天达标，现在它认为全部达标了。但问题是：修正循环是基于 LLM 自己估算的热量，而不是确定性计算的热量。

周一标注 2561 但实际 2339（差 222 kcal），核心原因是"彩椒牛肉丝"标注 712 kcal 实际只有 582 kcal（+22.4%偏差）。周四标注 2672 实际 2414（差 258 kcal），核心原因是"金枪鱼红薯"标注 508 实际 404（+25.6%）和"烤鸡腿配红薯"标注 894 实际 802（+11.5%）。

修正循环让标注值达标了，但因为标注本身有偏差，实际值仍然差距。这再次印证了 system review 中的结论：必须引入食物营养数据库做确定性计算，才能从根本上解决这个问题。

03 需要解决的问题
🔴修正循环基于 LLM 估算值，而非确定性计算P0
修正循环已经实现了——这是好消息。但它修正的依据是 LLM 自己估的热量，而 LLM 在某些菜品上系统性高估（牛肉丝 +22%、金枪鱼红薯 +26%）。这导致循环"自以为达标"但实际没达标。解法仍然是引入食物营养数据库，让修正循环基于确定性计算值来判断是否达标。这是"最后一公里"——架构已到位，只差把估算替换成查表。
🔴周五结构异常：三餐都是鸡胸肉+米饭P0
周五的 pre_workout 是"快手鸡胸米饭"、lunch 是"鸡胸肉西兰花饭"、post_workout 是"快手鸡胸饭"——一天吃三顿鸡胸饭。且同时存在 lunch 和 post_workout 两个正餐级别的鸡胸饭（各 ~200g 米饭），餐食结构不合理。用户不会接受这种安排。

这暴露了一个多样性约束的缺失：同一天内同一主蛋白质来源最多出现 2 次。同时，训练日的餐食结构应该是固定模板（breakfast + pre_workout + post_workout + dinner + snack），不应该同时出现 lunch 和 post_workout。
🟠周三 pre_workout 863 kcal — 训练前加餐不该是正餐量P1
"香蕉燕麦能量球"标注 863 kcal（计算 853 kcal），作为训练前加餐远超合理范围。训练前 60-90 分钟吃 850 kcal 的食物会导致训练时胃部不适。需要约束：pre_workout.kcal ≤ 400。多余的热量应该分配到 breakfast 或 snack。
🟠周二 post_workout 蛋白质仅 20g，且验证阈值过低P1
系统已经在检测 post_workout 蛋白质了（底部提示"训练后餐蛋白质 20g < 20g"），说明这个检测维度已加入。但阈值设成了 ≥20g 而非 ≥35g，导致这个几乎不会触发（20g 的鸡蛋香蕉奶昔刚好踩线）。应改为 post_workout.protein ≥ 35g。此外，这个验证应该触发修正循环（用高蛋白食材替换低蛋白的奶昔），而不是只输出文字提示。
🟡食材用量精度过高，用户无法执行P2
出现大量奇怪精度的数字：81g 面包、136g 鸡蛋、271g 红薯、203g 苹果、253g 鸡腿。这看起来是为了凑热量而精算到个位数。但用户的厨房秤精度通常是 1-5g，更重要的是没人会称出 203g 的苹果——苹果就是一个或半个。应该加约束：所有食材用量 round 到 5g 或 10g 整数，自然食材（苹果、香蕉、鸡蛋）用"个数"标注。
🟡周二"鸡蛋香蕉奶昔"— 熟鸡蛋打奶昔？P2
食材写"鸡蛋 136g (煮熟)"，步骤写"鸡蛋提前煮熟。将所有食材放入搅拌机"。把煮熟的鸡蛋和香蕉蓝莓一起打成奶昔，口感和味道会很糟糕。这不是一个用户会接受的食谱。如果需要高蛋白奶昔，应该用植物蛋白粉、嫩豆腐或希腊酸奶（无乳糖版）作为蛋白质来源。
04 做得好的地方
🆕菜品创新跨越式进步
虾仁汤面、三文鱼藜麦碗、烤鸡腿配红薯、浓香扁豆汤、金枪鱼红薯泥、豆腐莓果碗——这些都是 v2 没有的新菜品，覆盖了不同的蛋白质来源（虾、三文鱼、扁豆、鸡腿）、不同碳水（藜麦、面条）、不同烹饪方式（烤箱、煮汤）。食谱的整体吸引力大幅提升。
🔄修正循环已实现
这是架构层面的核心突破。v2 的系统只给文字提示，v3 真的在修正了——虽然基于 LLM 估算值有误差，但机制已到位。周六休息日热量从 v2 的 -14% 修正到 +0.1%，几乎完美。
💪蛋白质检测已加入
底部提示"训练后餐蛋白质 20g < 20g"，说明 post_workout 蛋白质验证已实现。阈值虽然设得太低（20g vs 建议的 35g），但框架已到位，调参即可。
✅乳糖限制持续合规
连续第二个版本无乳制品违规。豆腐、花生酱、植物油等替代方案稳定使用。

06 v4 改进优先级
1.接入食物营养数据库 → 确定性计算替换 LLM 估算P0
架构已到位（修正循环已实现），只差最后一步：把循环中的"LLM 估值"替换成"查表计算值"。这样修正循环就能基于真实热量做判断，7/7 的标注口径就能变成 7/7 的实际口径。
2.增加日内多样性约束 + 餐食结构模板P0
规则：同一天内同一蛋白质来源最多出现 2 次（防止周五三顿鸡胸饭）。训练日餐食结构固定为 breakfast + pre_workout + post_workout + dinner + snack（不应出现 lunch + post_workout 并存）。
3.每餐热量范围约束P1
pre_workout ≤ 400 kcal、snack 150-350 kcal、breakfast 400-700 kcal、lunch/dinner 500-1000 kcal。防止周三 pre_workout 863 kcal 这种极端情况。
4.post_workout 蛋白质阈值调整为 ≥35gP1
当前阈值 ≥20g 几乎不会触发。调整到 ≥35g，并让验证不通过时触发食材替换（如用鸡胸肉或蛋白粉替换水果奶昔）。
5.食材用量四舍五入 + 食谱合理性检查P2
所有用量 round 到 10g（自然食材用个数）。增加食谱合理性检查：不允许"煮熟鸡蛋打奶昔"这种组合。

B+：架构突破到位，离 A- 差"确定性计算"这最后一步

v3 实现了两个关键架构突破：自动修正循环（热量标注口径从 4/7 → 7/7）和 post_workout 蛋白质检测（虽然阈值偏低）。这两个是 v1/v2 review 中反复强调的核心缺陷，现在框架已经到位。

但实际热量达标率仍然是 4/7——因为修正循环信任了 LLM 的估值。这不是循环本身的问题，而是"最后一公里"：把 LLM 估算替换成食物营养数据库的确定性计算。一旦这步完成，当前 4/7 的实际达标率就有望提升到 6-7/7。

同时暴露了新问题：日内多样性（周五三顿鸡胸饭）和餐食热量分布（周三 pre_workout 863 kcal）缺少约束规则。这些可以通过增加 2-3 条规则解决，不需要架构变更。

从"用户不动脑子跟着执行"的标准看：大部分天数已经可以直接执行——周二、周三、周六的计划质量很高，食谱有吸引力、热量达标、蛋白质充足。但周五（三顿鸡胸饭）和周二的"煮鸡蛋打奶昔"会让用户质疑计划的可靠性。消除这类"明显不合理"的输出，比热量差 5% 更重要。

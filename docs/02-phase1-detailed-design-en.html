Phase 1 · Detailed Design

Planning Agent Detailed Design

The goal of Phase 1 is to complete the full capability set of the Planning Agent as a standalone system. It starts from "generate a plan once" and evolves into an intelligent fitness concierge that can interact, understand schedules, learn continuously, and close the loop with monitoring. It is organized into four sub-versions: static planning (v0.1.x), dynamic interaction (v0.2.x), self-evolution (v0.3.x), and monitoring with feedback (v0.4.x).
01 v0.1.x · Static Planning
v0.1.0 User Initialization + Basic Plan Generation
This is the starting point of the system. It collects user information through structured Q&A, then uses PlanAgent and the knowledge base to generate a personalized weekly training plan and daily nutrition program. After generation, the plan passes through multiple rounds of generate → validate → revise to ensure quality, including training-volume checks, calorie alignment, and injury safety. This version is already largely implemented and has gone through several rounds of validation.

📊 What the Plan Outputs PlanAgent
Daily nutrition targets (calories / protein / carbs / fat), recommended meal structure (breakfast, lunch, dinner, plus snacks with substitution options), a 5-day weekly training split (warm-up → main workout table → stretching each day), starting weights and set/rep guidance for each exercise, a 4-week progression framework, and coach-style notes covering progression rules, injury precautions, and recovery advice.
v0.1.x Fine-Grained Guidance — Detailed Execution via Sub-Agents
The Plan generated in v0.1.0 is the "skeleton": it tells the user what to train and what to eat each day. But users may not know how to actually prepare "150g chicken breast + 200g brown rice", or how to execute every detail of a "dumbbell Romanian deadlift". v0.1.x introduces specialized sub-agents to generate much more detailed Guidance, turning the Plan from a menu into a recipe with steps and a workout card with coach-level cues.
🍳 CookingAgent
Fine-grained nutrition guidance
Receives the targets from the Plan and generates cooking steps, grocery lists, and substitution options. The core design is "LLM creativity + deterministic post-processing" so every gram of macros stays aligned with the plan.
Recipe Steps Grocery List Macro Validation
🥡 TakeoutAgent
Takeout and dine-in ordering strategy
Designed for "no time to cook" scenarios. It uses a takeout knowledge base of chain brands and common categories to recommend orders and flag common pitfalls, keeping nutritional drift under control during busy or social situations.
Ordering Guide Pitfall Avoidance Calorie Alignment
🏋️ GYMAgent
Fine-grained training guidance
Generates concrete execution cues, injury-adapted alternatives, and a 4-week progression table. It turns the Plan into a workout-specific task card that guides execution quality.
Movement Cues Progression Table Workout Task Card
⚠️ InjuriesAgent
Injury analysis and day-to-day advisory
Investigates injury details and maps vague user descriptions into precise contraindications. Beyond filtering exercises, it also provides day-to-day correction advice such as sedentary reminders and rehab stretching.
Precise Contraindications Daily Activity Advice Rehab Tips
📊 GoalConfigAgent
Profile and goal calibration
Acts as a preprocessor that dynamically adjusts activity multipliers and calorie deficits using richer user context such as occupation, commute, and body-fat level, while checking whether the goal is scientifically reasonable.
TDEE Calibration Scientific Deficit Goal Feasibility Check
💊 SupplementAgent
Supplement recommendation specialist
Recommends supplements such as creatine, protein powder, or vitamins based on training intensity and dietary gaps, including precise timing guidance.
Supplement List Timing Schedule Deficiency Alerts
🛌 RecoveryAgent
Recovery and sleep planning
Plans detailed sleep guidance for training days, including duration and environment, and active-recovery plans for rest days such as foam rolling and stretching.

🔬 ScientificAdvisoryAgent
Scientific rationale and explanation
Provides the scientific explanation behind the plan. It cites research to explain nutrition ratios and training logic, improving credibility and professional trust.

💰 BudgetAgent
Fitness budget management
Estimates spending across food, supplements, and equipment, then recommends tiered options based on the user's budget, from lean student setups to more advanced configurations.

👟 ApparelAgent
Equipment advisor

🧘 BehaviorAgent
Habit design and adherence optimization
Designs triggers and habit anchors inside daily life. The goal is to reduce the psychological friction of starting training and improve long-term adherence.

🔐 Resource Governance and Dynamic Permission Architecture Registry

To support multi-agent collaboration, the system introduces a Resource Registry:

  • Permission isolation: each sub-agent can only access the knowledge bases relevant to its role, such as CookingAgent using the recipe library and InjuriesAgent using the injury and condition library.
  • Dynamic maintenance: knowledge bases and tools are decoupled from agent logic, so KBs can be updated online and tools such as calendars or calculators can be hot-plugged.
  • Entrance-driven intake: EntranceAgent dynamically generates onboarding questions from the field requirements of downstream sub-agents using a Requirement KB, ensuring the profile is collected on demand instead of all at once.

02 v0.2.x · Dynamic Interaction
v0.2.0 Conversational Adjustments — One Change Ripples Through Everything
The plans in v0.1.x are generated once, but real life keeps changing. v0.2.x gives the system the ability to talk with the user and adjust dynamically. The core challenge is that local edits require global updates. If the user says, "I want noodles for dinner today," the system cannot simply swap one meal. It has to recalculate the day's calorie distribution and may need to adjust other meals to compensate. If the user says, "I have to work late on Wednesday and can't train," the system must redistribute Wednesday's training volume to other training days so weekly volume does not collapse.
🔗 Cascading Adjustment Examples
💬 "I want noodles for dinner tonight"
→
Replace the dinner recipe Recalculate dinner calories Adjust lunch/snacks to compensate Update the grocery list
💬 "I have to work late on Wednesday and can't train"
→
Cancel Wednesday training Redistribute volume to other days Adjust Wednesday nutrition for a non-training day Update weekly volume validation
💬 "My knees feel a bit uncomfortable when I squat"
→
Replace squats with lower-knee-stress movements Adjust lower-body programming Update the injury record Recommend medical evaluation
💾 Conversation History and State Persistence State
Every user interaction needs to be recorded and persisted. The system must maintain the currently active Plan version, while creating a new version and preserving history for every adjustment; a cumulative record of user preferences such as "I don't like chicken breast" or "I prefer running on weekends"; and the reason and context behind each adjustment so agents can proactively avoid similar conflicts in the future. These records are also the base data KBAgent uses in v0.3.x to understand user preferences.
v0.2.x Schedule Awareness — Proactively Adapting to Real Life
The system evolves from "the user tells me what changed" to "I proactively sense what changed". By importing ICS calendar files or integrating calendar APIs, the agent can anticipate schedule changes and adjust training and nutrition plans ahead of time.
📅
Work Calendar
Detect meeting-heavy days → assign lighter sessions or recovery days. Detect travel dates → switch to hotel-friendly routines. Detect work end times → adjust pre- and post-workout meal timing.
🩸
Menstrual Cycle Tracking
Menstrual phase → reduce training intensity and increase iron intake. Follicular phase → support higher-intensity training. Luteal phase → emphasize recovery and reduce heavy lifting. The plan adapts automatically to the cycle.
✈️
Travel and Social Events
During travel → provide no-equipment training options. For social meals → adjust the calorie budget of the rest of the day. For holidays → switch to a flexible mode that allows measured relaxation.
😴
Routine and Recovery
Lack of sleep → reduce training volume. After multiple high-intensity days → proactively insert extra recovery. During exam or deadline weeks → simplify the program to reduce mental load.
📎 ICS Files / Calendar API Integration Data Source
Users can upload ICS files or connect Google Calendar / Apple Calendar. The agent parses calendar events, extracts key attributes such as time, location, and event type, estimates their impact on training and nutrition, and proactively adjusts the next day's plan in advance, for example the night before. Schedule changes also trigger cascading updates.
03 v0.3.x · Self-Evolution
v0.3.x KBAgent — Automatic Knowledge Base Evolution
The knowledge base is not static. KBAgent is responsible for making system knowledge continuously grow and improve. It works along two axes: acquiring new knowledge from the outside world, and shifting knowledge emphasis based on user preferences.
🌐 External Knowledge Acquisition
It gathers the latest exercise science and nutrition knowledge from the internet, academic papers, and authoritative books. Newly published findings, such as updated evidence on the optimal weekly volume for hypertrophy, can update rule-set parameters after credibility review. New training methods, recipes, and supplement information can also be added to the knowledge base. The key requirement is that every new piece of knowledge must pass validation, including source-credibility assessment and consistency checks against existing knowledge, before it is adopted.
👤 User Preference Adaptation
By analyzing historical conversations and behavior patterns, KBAgent proactively shifts the focus of the knowledge base. For example, if a user frequently asks vegetarian questions, it deepens knowledge around vegetarian protein sources and recipes. If the user repeatedly reports disliking a type of food, it expands substitute knowledge for that category. If the user prefers free weights over machines, it grows the corresponding library of exercise variations. This makes the knowledge base increasingly tailored to the individual user.
🔒 Safety Mechanisms for Knowledge Updates KBAgent
KBAgent does not update knowledge without constraints. The core safeguards include source credibility scoring for new information, with academic papers ranked above authorities, authorities above professional media, and professional media above generic webpages; conflict detection against the existing core rule set, so new knowledge cannot overwrite foundational safety rules directly; full update logs with rollback capability; and periodic human review checkpoints.
04 v0.4.x · Monitoring and Closed-Loop Feedback
v0.4.x MonitorAgent — Expected vs Actual + Continuous Course Correction
The earlier versions from v0.1.x to v0.3.x solve the problem of how to plan. But no matter how good the plan is, if the system does not know what the user actually did or what results it produced, the system remains open-loop. MonitorAgent is what turns it into a closed-loop system by continuously tracking real execution and body-metric changes, comparing them against expected targets, and triggering adjustments when deviations appear.
📊 The Two Core Objectives MONITOR
Objective 1: keep reality as close as possible to the plan — If the user planned to train 5 days this week, how many days did they really complete? If the plan calls for 2500 kcal per day, how much did they actually eat? If the plan expects 10 squat reps per set, how many were actually completed? Smaller deviations indicate a more executable plan; larger deviations indicate the plan needs adjustment.

Objective 2: keep key metrics moving in a positive direction — Is body weight changing as expected? Is strength progressing? Is body-fat trending in the right direction? Even if the user follows the plan strictly, if the metrics are not improving, the plan itself needs to be corrected.
📈 Expected vs Actual Dashboard (Dashboard Tool)
📋 Execution Tracking Dimensions
Training completion rate (planned vs actual training days)

Load progression (planned progression vs actual working weights)
Nutrition adherence (planned calories vs actual intake)

📏 Body Metrics Dimensions
Body-weight curve (expected trend vs actual trend)
Body-fat change (if data is available)
Strength curves for main lifts (squat / bench / deadlift)
Circumference changes (chest / arm / waist, if data is available)

The dashboard is a continuously updated visualization tool. Users can inspect their progress at any time, and MonitorAgent also uses these data streams to make decisions.
⚡ Automatic Adjustments Triggered by Deviations
📉 Training completion < 70% for 2 consecutive weeks
→
Diagnose the cause: too hard or no time? PlanAgent lowers training frequency or volume Proactively ask the user about blockers
📉 No body-weight change for 2 weeks (muscle-gain goal)
→
Check nutrition adherence CookingAgent increases calories by 150-200 kcal Flag it for review next week
📈 Strength on a lift plateaus for 3 consecutive weeks
→
GYMAgent adjusts the progression strategy for that lift Introduce exercise variations or a new set/rep scheme Check whether a deload week is needed
⚠️ Nutrition drifts from the plan over the long term
→
Analyze the drift pattern: which meals, which food types? CookingAgent adjusts the plan to better match actual eating habits Update the user preference record
📱 Data Collection Modes Interaction
MonitorAgent needs data to work, but collecting that data cannot create too much friction for the user. Data comes from three sources:

Active logging (low frequency, high value) — Weigh-ins once or twice per week with reminders, body-fat or circumference measurements once per month, and one-click completion logging after training.

Conversational capture (natural and low burden) — Information mentioned casually in normal conversation, such as "I had hotpot for lunch" or "I slept badly last night", is extracted and logged automatically by the agent without requiring dedicated reporting.

Automatic inference (zero-cost) — If the user does not mark a workout complete, infer it was missed. If there are no nutrition records for 3 days, mark adherence as unknown. If the calendar shows travel, infer that training conditions are constrained.

05 Phase 1 at a Glance

From Static to Dynamic to Self-Evolving to Closed Loop

The core logic of Phase 1 is a clear evolutionary path. v0.1.x solves the question of whether the system can generate a good plan at all, and is already mostly complete. The later part of v0.1.x uses sub-agents to make each detail of the plan concrete and executable. v0.2.x solves whether the plan can adapt to real life. v0.3.x solves whether the system's knowledge can keep improving. v0.4.x solves whether the system knows what impact the plan is actually having, completing the most important missing piece: the feedback loop.

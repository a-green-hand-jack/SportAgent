Phase 1 · Detailed Design

规划 Agent 详细设计

Phase 1 的目标是独立完成规划 Agent 的全部能力。从"一次性生成计划"出发，逐步进化为"能交互、能感知日程、能自我学习"的智能健身管家。分为三个子版本：静态规划（v0.1.x）、动态交互（v0.2.x）、自进化（v0.3.x）。
01 v0.1.x · 静态规划
v0.1.0 用户初始化 + 基础 Plan 生成
系统的起点。通过结构化问答收集用户信息，由 PlanAgent 基于知识库生成个性化的周训练计划和每日营养方案。计划生成后经过多轮"生成-验证-修正"循环确保质量（训练量达标、热量匹配、伤病安全）。这个版本已经基本实现并经过了多轮迭代验证。

🧠 PlanAgent：大脑核心与多维约束编排 PlanAgent

PlanAgent 是系统的中枢，负责将抽象的用户目标转化为具体的周计划。其核心理念是“在确定性约束下的 LLM 创意生成”。

核心逻辑：
  • KB 预过滤 (Deterministic Filtering)：在调用 LLM 之前，系统会根据用户的伤病标签和可用器械，从海量动作库中预先过滤出“非法动作”，确保 LLM 只在安全圈内进行创作。
  • 多阶段验证循环 (GVC Loop)：采用“生成 (Generate) - 验证 (Validate) - 修正 (Correct)”架构。通过确定性脚本（如训练量计算、时长估算）对计划进行扫描，若发现容量不足或强度违规，则将错误反馈给 Agent 进行局部重写。
  • 结构化输出控制：通过 Pydantic 模型强制 LLM 返回符合规范的 JSON，确保下游的 Guidance 子智能体能够无缝解析和二次处理。
实现说明：
  • Prompt Engineering：采用 CoT（思维链）引导，让 Agent 先思考用户的能量缺口和训练频率，再进行排课，避免逻辑跳跃。
  • 验证字典 (Warning System)：内置训练量基准规则（如：初学者每周每块肌肉 8-10 组）。若校验失败，会将具体的 Warn Message 返回给 LLM，实现自我进化的生成路径。
💬 EntranceAgent：对话式入口与画像构建 EntranceAgent

针对“静态表单用户体验差、信息采集不全”的问题，EntranceAgent 将初始化流程从过程式 Q&A 升级为基于 LLM 的对话系统。

核心功能：
  • 对话识别与特征提取：利用 LLM 将用户口语化的描述（如“我平时坐班多，腰不太舒服”）精准转化为结构化的 Profile 字段（职业：坐班；潜在风险：Lower Back）。
  • 需求驱动补全 (Requirement-Driven)：通过检索 Requirement KB，识别当前所有已部署 Sub-Agents（如 GYM, Cooking）所依赖的必填项。
  • 动态追问策略：基于当前 Profile 的空缺项，采用“自然对话 + 针对性追问”的方式填充缺失信息，而非机械的问卷调查。
实现说明：
  • 逻辑内核：采用 LLM + Function Calling 模式。LLM 负责维持教练人设并引导对话，由 Function 实时解析用户意图并尝试更新结构化 UserProfile 模型。
  • 字段依赖注册表：建立一个 onboarding_requirements.json，每个 Sub-Agent 在此声明其所需的参数（如 GYM 需要器材列表和伤病标签）。EntranceAgent 会自动合并这些依赖作为对话终点。
  • 中间层校验：在 LLM 解析后，引入 Pydantic 校验层，确保采集到的身体数据（身高、体重等）符合科学范围，否则触发即时纠错对话。
v0.1.x 精细化 Guidance — 子 Agent 细粒度指导
v0.1.0 生成的 Plan 是"骨架"——它告诉用户每天练什么、吃什么。但用户可能不知道"鸡胸肉 150g + 糙米饭 200g"具体怎么做，也不知道"哑铃罗马尼亚硬拉"的每个细节该怎么执行。v0.1.x 引入专门的子 Agent 来生成更细粒度的 Guidance（指导），把 Plan 从"菜单"变成"带步骤的食谱"和"带教练提示的训练卡"。

饮食精细化指导
接收 Plan 目标，生成烹饪步骤、采购清单、替换方案。核心在于「LLM 创意 + 确定性后处理」，确保每一克的宏量素都符合规划。
食谱步骤 采购清单 热量验证
🥡 TakeoutAgent
外卖/堂食点餐策略
针对「无暇下厨」场景。基于外卖知识库（连锁品牌、常见品类）提供点餐选择与避坑指南。确保社交与忙碌时的营养偏差在可控范围内。
点餐指南 外卖避坑 热量对齐
🏋️ GYMAgent

⚠️ InjuriesAgent

深挖伤病细节，将模糊描述映射为专业禁忌。除了过滤动作，更提供日常活动修正建议（如久坐提示、康复性拉伸）。

📊 GoalConfigAgent

💊 SupplementAgent
补剂建议专家

补剂清单 服药时间表 缺失营养提醒
🛌 RecoveryAgent
恢复与睡眠规划
规划训练日的详细睡眠建议（时长、环境）及休息日的「积极恢复」方案（如泡沫轴放松、拉伸等）。
睡眠指南 积极恢复方案 疲劳监测
🔬 ScientificAdvisoryAgent
科学背书与原理解析
为计划提供科学解释。引用研究文献解释营养配比与训练逻辑，提升计划的可信度与专业感。

💰 BudgetAgent
健身财务预算管理
估算饮食、补剂及装备的开销。根据用户预算分级推荐方案（如“学生极简型”或“进阶专业型”）。

🔐 资源管控与动态权限架构 Registry

为了支撑多 Agent 协作，系统引入资源注册表（Resource Registry）机制：

  • 权限隔离：不同 Subagent 仅能访问其职能相关的知识库（如 CookingAgent 访问食谱库，InjuriesAgent 访问疾病库）。
  • 动态维护：知识库与工具独立于 Agent 逻辑，可在线更新 KB 或热插拔 Tools（日历、计算器等）。
  • Entrance 驱动：EntranceAgent 根据后台其他 Subagent 的字段需求（Requirement KB）动态生成引导问题，确保 Profile 的按需采集。

02 v0.2.x · 动态交互
v0.2.0 对话式调整 — 牵一发而动全身
v0.1.x 的计划是"一次性生成"的，但现实中用户的需求时刻在变化。v0.2.x 让系统具备与用户对话并动态调整的能力。核心挑战：局部修改需要触发全局调整。用户说"今天想吃面条"，系统不能只是换一餐——它需要重新计算这一天的热量分配，可能还要调整其他餐来补偿营养差异。用户说"周三加班不能练了"，系统需要把周三的训练量重新分配到其他训练日，确保周训练量不下降。
🔗 级联调整示例
💬 "今天晚餐想吃面条"
→
替换晚餐食谱 重算晚餐热量 调整午餐/加餐补偿 更新采购清单
💬 "周三要加班没法练"
→
取消周三训练 重分配训练量到其他日 调整周三饮食（非训练日热量） 更新周训练量验证
💬 "做深蹲膝盖有点不舒服"
→
替换深蹲为低膝盖压力动作 调整下肢训练编排 更新伤病记录 建议就医检查
💾 对话记录与状态持久化 状态
每次用户交互都需要被记录和持久化。系统需要维护：当前活跃的 Plan 版本（每次调整生成新版本，保留历史）、用户偏好的累积记录（"不喜欢吃鸡胸肉"、"周末更喜欢跑步"）、调整的原因和上下文（方便 Agent 在未来主动避免类似冲突）。这些记录也是 v0.3.x KBAgent 理解用户偏好的基础数据。
v0.2.x 日程感知 — 主动适配用户生活
从"用户告诉我变化"进化为"我主动感知变化"。通过导入 ICS 日历文件或对接日历 API，Agent 能提前感知用户的日程安排，主动调整训练和饮食计划。
📅
工作日历
识别会议密集日 → 安排轻量训练或休息日。识别出差日期 → 切换为酒店可执行方案。识别下班时间 → 调整训练前后饮食时间窗口。
🩸
经期追踪
经期阶段 → 降低训练强度，增加铁质摄入。卵泡期 → 适合高强度训练。黄体期 → 关注恢复，减少大重量训练。根据周期自动调整计划。
✈️
出行与社交
旅行期间 → 提供无器材训练方案。朋友聚餐 → 调整当天其他餐热量预算。节假日 → 弹性方案，允许适度放松。
😴
作息与恢复
睡眠不足 → 降低训练容量。连续高强度训练后 → 主动安排额外恢复日。考试/deadline 周 → 简化方案减轻心理负担。
📎 ICS 文件 / 日历 API 集成 数据源
用户可以上传 ICS 文件或连接 Google Calendar / Apple Calendar。Agent 解析日程事件，提取关键信息（时间、地点、类型），判断对训练和饮食的影响，并提前（比如前一天晚上）主动调整次日的计划。日程变更也会触发级联调整。
03 v0.3.x · 自进化
v0.3.x KBAgent — 知识库自动进化
知识库不是一成不变的。KBAgent 负责让系统的知识持续增长和优化。它有两个维度的工作：从外部世界获取新知识，以及根据用户的偏好调整知识侧重。
🌐 外部知识获取
从互联网、学术论文、权威书籍中获取最新的运动科学和营养学知识。新发表的研究结果（如"最新研究表明每周 12-20 组训练量对增肌最优"）经过可信度评估后可以更新规则集中的参数。新的训练方法、食谱、营养补剂信息也可以被纳入知识库。关键：所有新知识必须经过验证流程（来源可信度评估 + 与现有知识的一致性检查）才能被采纳，避免引入错误信息。
👤 用户偏好适配
通过分析用户的历史对话和行为模式，KBAgent 主动调整知识储备的侧重方向。比如用户经常问素食相关问题 → 主动丰富素食蛋白质来源和素食食谱知识。用户多次反馈某类食物不喜欢 → 自动扩展该类食物的替代品知识。用户的训练偏好（喜欢自由重量 vs 器械）→ 丰富对应方向的动作变体知识。这让系统的知识库成为"为这个用户量身定制"的。
🔒 知识更新的安全机制 KBAgent
KBAgent 的更新不是无约束的。核心安全机制包括：新知识的来源可信度评分（学术论文 > 权威机构 > 专业媒体 > 普通网页）、与现有核心规则集的冲突检测（新知识不能直接覆盖核心安全规则）、更新记录和回滚能力（每次更新都有完整日志，发现问题可以回滚）、以及定期的人工审核检查点。
04 v0.4.x · 监控与反馈闭环
v0.4.x MonitorAgent — 预期 vs 真实 + 持续纠偏
前面的 v0.1.x ~ v0.3.x 解决的是"怎么规划"的问题，但规划再好，如果不知道用户实际做了什么、效果如何，系统就是"开环"的。MonitorAgent 负责把系统变成"闭环"——持续追踪用户的真实执行情况和身体指标变化，与预期目标对比，在偏差出现时及时触发调整。
📊 核心双目标 MONITOR
目标一：真实情况尽可能贴合预期 — 用户这周计划练 5 天，实际练了几天？计划每天摄入 2500 kcal，实际吃了多少？计划每组深蹲做 10 次，实际完成了几次？偏差越小说明计划的可执行性越好，偏差越大说明计划需要调整。

目标二：指标持续向好的方向发展 — 体重是否在按预期变化？力量是否在渐进提升？体脂率的趋势是否正确？即使用户严格执行了计划，如果指标没有向好的方向发展，说明计划本身需要修正。
📈 预期 vs 真实 仪表盘（Dashboard Tool）
📋 执行追踪维度
训练完成率（计划 vs 实际训练天数）
单次训练完成度（计划动作 vs 实际完成）
重量进展（计划渐进 vs 实际使用重量）
饮食遵从度（计划热量 vs 实际摄入）

仪表盘是一个持续更新的可视化工具。用户可以随时查看自己的进展，MonitorAgent 也基于这些数据做出判断。

📱 数据采集方式 交互
MonitorAgent 需要数据才能工作，但数据采集不能给用户增加太多负担。数据来源分为三类：

主动记录（低频、高价值） — 每周 1-2 次称体重（提醒式）、每月 1 次体脂/围度测量、训练后标记完成状态（一键操作）。

对话式采集（自然、无负担） — 用户在日常对话中透露的信息（"今天中午吃了火锅"、"昨晚没睡好"）由 Agent 自动提取并记录，无需用户专门汇报。

自动推断（零成本） — 用户没有标记训练完成 → 推断为未完成。连续 3 天没有饮食记录 → 标记为饮食遵从度未知。日历显示出差 → 推断训练条件受限。

这是整个 Phase 1 的完整闭环：规划 → 执行 → 监控 → 反馈 → 再规划。MonitorAgent 是把"开环系统"变成"闭环系统"的关键。
05 Phase 1 全景一览

从静态到动态到自进化到闭环

Phase 1 的核心逻辑是一条清晰的进化路径：v0.1.x 解决"能不能生成一个好计划"的问题（已基本完成），v0.1.x 的后半段通过子 Agent 解决"计划的每个细节是否足够具体和可执行"的问题，v0.2.x 解决"计划能不能适应用户的真实生活"的问题，v0.3.x 解决"系统的知识能不能持续进步"的问题，v0.4.x 解决"系统知不知道计划的效果如何"的问题——补上反馈闭环这最关键的一环。

版本 核心能力 涉及的 Agent 用户体验变化
v0.1.0 基础 Plan 生成 + 多轮验证 PlanAgent 输入信息 → 得到一个周计划
v0.1.x 精细化 Guidance（食谱 + 训练卡） PlanAgent + CookingAgent + GYMAgent 得到完整的、可直接执行的每日指南
v0.2.0 对话式调整 + 级联更新 PlanAgent + CookingAgent + GYMAgent 可以随时说"我想改…"，系统自动调整全局
v0.2.x 日程感知（ICS / 经期 / 作息） PlanAgent + CalendarSync 系统主动根据日程调整计划，用户无需操心
v0.3.x 知识库自动进化 KBAgent + PlanAgent 系统越用越懂我，知识越来越新
v0.4.x 监控反馈闭环 + 仪表盘 MonitorAgent + PlanAgent + CookingAgent + GYMAgent 系统知道我做了什么、效果如何，自动纠偏
